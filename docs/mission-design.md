# 旅行プラン・ミッション設計

担当: 多田 / 目的: ミッションを「技術的に判定できる範囲」で設計し、判定仕様を決める。
議事録(8/22 12:14 MTG)の決定事項ベース: 固定プランベース、判定はカメラ/AR/GPS、Live Activity で進捗表示、心拍×写真で感情の瞬間を特定。

## 1. 基本方針: 判定は「写真 + GPS」に統一

すべてのミッションは **「アプリ内カメラで写真を撮る」ことで達成申請**し、判定は共通パイプライン 1 本で行う:

```
撮影(アプリ内カメラ)
  → その瞬間の GPS を取得
  → [GPS 条件] 目標地点の半径内か(条件がある場合のみ)
  → [AI 判定] 写真がお題を満たすか(Gemini / GPT 画像判定に Yes/No で質問)
  → 達成: Watch 触覚 FB + Live Activity 更新 / 未達: 理由を一言返してリトライ
```

利点:
- 判定実装が 1 本で済む(ミッション追加は JSON を書くだけ)
- どんなお題も生成 AI プロンプトで表現できる(自由度が高い)
- **全ミッションで写真が残る** → 心拍×写真の照合、結果レポート、Journaling 素材にそのまま使える
- 山本さんの API 検証(画像判定系)と直結

心拍・触覚はミッション判定ではなく体験レイヤー:
- 接近時・達成時に Watch 触覚 FB
- 心拍は旅行中ずっとバックグラウンド記録 → 集中スコアと「感情が動いた瞬間」抽出に使用

## 2. 判定モジュール(基本 2 + AR 拡張 3)

「写真+GPS」を基本としつつ、技術アピール用に AR 判定を上乗せモジュールとして持つ。

| 判定タイプ | 技術 | 内容 | 難度 |
|-----------|------|------|------|
| `photo` | カメラ + 生成 AI | 写真がお題を満たすか Yes/No | 低(基本) |
| `location` | CoreLocation | 目標半径内か | 低(基本) |
| `face` | ARKit Face Tracking(TrueDepth) | 表情判定: 笑顔(mouthSmile)などを blendShapes でリアルタイム判定。**口角の上がり具合と顔メッシュを画面に可視化**し、達成の瞬間を自動撮影 | 中 |
| `body` | ARKit Body Tracking | ポーズ判定: 万歳など(joint 位置)。**骨格(ジョイント)を画面に可視化**し、達成の瞬間を自動撮影 | 中〜高 |
| `vps` | ARCore Geospatial API(チームの Google Cloud キーで有効化済み) | cm 級の位置+向き判定 ※スタンプラリー形式は体験とズレるため除外。採用するなら GO 到着時の AR 演出などに限定(保留) | 高 |

- `face` / `body` は「判定した瞬間にフレームを自動保存」することで、写真が残る設計を維持(心拍照合・レポート素材)
- VPS は Apple の ARGeoTracking が日本非対応のため **ARCore Geospatial API を採用**(Street View カバレッジで東京の屋外は動く。API キーは発行済み)
- AR 判定はデモ映え最優先。実装が間に合わない場合は `photo`(AI 判定)に必ずフォールバックできるお題設計にしておく(例: 笑顔 → 笑顔の自撮りを AI 判定)

## 2.5 ミッションカテゴリ(固定 + 変動)

プランは **固定カテゴリ(毎プラン必ず入る基本 3 種)+ 変動カテゴリ(プランごとに差し替わる枠)** で構成する。

### 固定カテゴリ(全プラン共通・写真+GPS 判定で完結)

| カテゴリ | 内容 | 判定タイプ | 例 |
|----------|------|-----------|----|
| **GO(行く)** | どこかへ行く | location + photo | 東京タワーへ行く |
| **DO(する)** | 何かをする | photo (+location) | タワーを真下から撮る、鳥居をくぐる |
| **EAT(食べる)** | 何かを食べる | photo | かき氷を食べる |

### 変動カテゴリ(プランごとに選択・技術/演出枠)

| カテゴリ | 内容 | 判定タイプ | 例 |
|----------|------|-----------|----|
| **FACE(表情)** | 指定の表情を現地で | face(Face Tracking) | 絶景の前で最高の笑顔、変顔をする |
| **POSE(ポーズ)** | 指定ポーズを現地で | body(Body Tracking) | 大仏と同じポーズをする、万歳する |
| **BUY(買う)** | お土産・ご当地品を買う | photo | 500円以内で「いちばん良い」お土産を買う |
| **FIND(探す)** | 現地でお題の被写体を探す | photo | 「いちばん夏っぽいもの」を撮る、赤い提灯を見つける |
| **QUIZ(答える)** | 現地でしか分からない謎 | location + テキスト入力 | 「狛犬は何体いる?」に現地で答える |

- 除外決定: **STAMP(AR スタンプラリー)** は体験とズレるため除外。**CALM(眺める)** はそもそもスマホをほぼ使わせない前提なので不要。**THRILL(ドキドキ)** はリアルタイム心拍判定の難度が高いため除外(心拍はミッション判定ではなく、旅行全体の記録としてリザルトの「心拍のゆらぎ」スコアで活かす)
- QUIZ は判定が簡単(文字列一致)な割に「現地に行かないと解けない」体験が作れるコスパ枠
- 5 ミッション構成 = **固定 3(GO + DO + EAT)+ 変動 2**。変動枠の推奨は FACE + POSE(AR 技術枠。トラッキング状態を画面に可視化する)

## 3. ミッションデータモデル

```json
{
  "planId": "trial-tokyo",
  "title": "はじめての東京旅",
  "missions": [
    {
      "id": "m1",
      "order": 1,
      "category": "go",
      "title": "東京タワーへ行く",
      "judgment": {
        "location": { "latitude": 35.6586, "longitude": 139.7454, "radiusMeters": 150 },
        "aiPrompt": "この写真に東京タワーが写っていますか?"
      },
      "hapticOnNear": true,
      "points": 10
    },
    {
      "id": "m2",
      "order": 2,
      "category": "do",
      "title": "笑顔の写真を撮る",
      "judgment": {
        "location": null,
        "aiPrompt": "この写真に笑顔の人が写っていますか?"
      },
      "camera": "front",
      "points": 10
    },
    {
      "id": "m3",
      "order": 3,
      "category": "eat",
      "title": "かき氷を食べる",
      "judgment": {
        "location": null,
        "aiPrompt": "この写真にかき氷が写っていますか?"
      },
      "points": 10
    }
  ]
}
```

- プランは固定 JSON をアプリ内バンドル(バックエンド不要)
- `judgment.location` は**案内・接近振動用**(LA の「◯◯から △m」表示と Watch 接近振動)。go 以外にも spot があれば付ける。`location.name` が案内表示名
- 判定ゲートに使うのは `judgment.locationRequired: true` のミッションのみ(通常 go だけ)。それ以外は場所を外れていても AI 写真判定のみで達成できる(判定は緩く、案内は手厚く)
- `judgment.location` が null なら GPS 判定・案内とも無し(eat など目的地のないお題)
- `camera`: front / back(デフォルト back)
- Live Activity には「現在のミッション order / title / 進捗」を表示

## 4. 仮旅行プラン

### 4-1. 実験用プラン(自宅周辺でテスト可能)

1. **[GO/固定]** 近所の公園 or コンビニへ行く(任意の座標に差し替えてテスト)
2. **[DO/固定]** 緑色のものを撮る
3. **[EAT/固定]** 飲み物 or お菓子を撮る
4. **[FACE/変動]** 笑顔を作る(Face Tracking テスト)
5. **[POSE/変動]** その場で万歳する(Body Tracking テスト)

### 4-2. デモ用プラン(発表向け・技術アピール構成)

固定 3 + 変動 2 の構成:

1. **[GO/固定]** 東京タワーへ行く(GPS + 写真 AI 判定、接近で Watch 振動)
2. **[DO/固定]** タワーを真下から撮る(写真 AI 判定)
3. **[EAT/固定]** かき氷を食べる(写真 AI 判定)
4. **[FACE/変動]** タワーをバックに最高の笑顔(Face Tracking が口角をリアルタイム可視化 → 笑顔キープで自動撮影)
5. **[POSE/変動]** タワーの前で万歳する(Body Tracking が骨格を可視化 → ポーズキープで自動撮影)

→ 5 つで「GPS / AR 表情 / AR 骨格 / 生成 AI」の技術要素をデモできる構成。心拍は旅行全体で記録し、リザルトの「心拍のゆらぎ」スコアで見せる。

## 5. スコアと勝敗ロジック(正式名称決定)

スコアは以下の 3 要素の合計(15:00 MTG で 3 要素に決定、名称は正式版):

1. **QUEST SCORE** — ミッションをどれだけ達成したか(達成 pt 合計)
2. **HEART SCORE** — どれだけ心が動いたか(心拍数の上下 = ワクワク・感動。移動平均からの偏差)
3. **OFFLINE SCORE** — どれだけスマホを見ずに過ごしたか(制限数ボーナス + 見なかった時間。利用時間・起動時間が少ないほど加点)

- **競争要素よりも個人の旅行満足度を優先**し、その上でメンバー間比較ができる構成にする(ガチガチの勝負にはしない)
- 勝利条件は体験内容に応じて変える → プラン JSON に `scoringProfile` で重み変更
- 結果画面では心拍×写真撮影時刻の突合による振り返りセクションも用意(何を入れるかは要検討)

## 6. プラン生成の仕組み(3 層ハイブリッド)

全自動生成は「難しすぎ/単調すぎ/実在しない場所」のリスクがあるため、役割を 3 層に分ける:

```
① 構造 = 完全固定(コード)
   プラン = 固定3(GO+DO+EAT) + 変動2。AI に型を任せない
② 事実 = 実データ(Google Places / Geocoding API ※キー有効化済み)
   スポット名・座標・営業時間は Places の実データ。AI に座標を書かせない
③ 味付け = LLM(Gemini/GPT)
   スポット候補からテーマに合う組み合わせを選び、ミッション文言と aiPrompt を生成。
   制約:「スマホカメラで撮影でき、写真1枚で Yes/No 判定できるお題」を強制
   + 生成後に「このお題は判定可能か?」を自己チェック
```

### エリア選択(決定: ピン設置 → 主要地スナップ)

```
ピン設置(MapKit) → 座標取得
  ① Geocoding 逆引き(例: 初台 → 「渋谷区初台」)
  ② Places Nearby(半径5km・観光スポット・注目度順) → 新宿御苑、都庁展望台…
  ③ LLM が ①+② から主要エリア名を確定(→「新宿」)、そのスポット群でプラン生成
```

- ピンが初台でも ② の注目度順検索で自然と新宿の主要スポット群が返る = **プランの中身は ② の時点で主要地の旅になる**。③ は表示用エリア名の確定
- 生成前に「新宿エリアでプランを作ります」の確認を 1 枚挟む(推定ズレの保険)
- スポットが少ない場合は半径を 5→10→20km と段階拡大
- 「現在地から始める」ボタンを併置。デモ安全策としておすすめエリアのショートカットも配置
- 自由入力は表記ゆれ処理が面倒なため不採用。**ミッションは確定した主要エリアのスポット群に紐づけて生成**

### 食べ物(決定: 地域名物ベース・店指定なし)

- EAT = **エリアの名物料理を AI が提案**(仙台=牛タン・ずんだもち、大阪=たこ焼き・どて煮 など)
- GPS 条件なし、判定は写真 AI のみ(どの店で食べても OK)
- 名物が出ないマイナーエリアのみ、フォールバックで「Places で実在確認した店で何か食べる」(店ベース)に落とす

### 人数ルールベース(ミッション内容・判定基準を人数で変える)

プラン作成 Step2「だれと」の人数に応じて、お題のトーンと判定基準を変える。
**判定基準は生成時に aiPrompt へ明示的に織り込む**(判定パイプライン自体は共通のまま)。

| 人数 | ミッション内容の方向性 | 判定基準(写真 AI) |
|------|------------------------|---------------------|
| 1 人(ひとり旅) | セルフィー・じっくり観察・内省系。「じぶんの◯◯」 | 人物条件は本人 1 人で OK。風景・モノだけの写真も可(FACE=自撮りで 1 人の笑顔 / POSE=セルフ万歳 1 人) |
| 2 人 | ペア系。「ふたりで◯◯」のお題にする | **2 人が写っていること**を aiPrompt に含める(FACE=2 人とも笑顔 / POSE=2 人とも万歳) |
| 3〜5 人 | グループ系。「全員で◯◯」のお題にする | **全員(N 人程度)が写っていること**+全員が条件を満たす(全員でジャンプ、全員で変顔 など) |

- AR 判定(FACE/POSE)は 1 人のトラッキングで自動撮影をトリガーし、**人数条件の最終確認は写真 AI が行う**(例: 2 人とも笑顔かは Gemini が判定)
- GO/EAT は人数の影響を受けにくいが、3 人以上では「全員で店の前で」など集合カットを混ぜてよい
- 判定の厳しさ調整: 人数ぴったりを要求せず「N 人以上」で判定(通行人の写り込みで落とさない)

### 難易度・単調さの制御

- 難易度は AI ではなく**パラメータ**で制御: GPS 半径(広い=易)、お題の抽象度(具体物=易・概念=難)、points
- 単調さは変動枠 2 つ+お題文言の差し替えで解消(構造が同じでも別の旅になる)

### 生成タイミングと安全策

- 生成は**旅行開始前に 1 回だけ**実行し JSON 保存(旅行中は通信不要で動く)
- 対戦相手とは同じ生成結果(JSON)を共有して公平に
- **手書きデモ用プランをバンドル同梱**。生成失敗時は即フォールバック

### 生成例

入力「浅草・3時間・まったり」→
1. [GO] 雷門へ行く(Places 座標 ±100m + 写真判定)
2. [DO] 仲見世で いちばん赤いものを撮る(AI 文言)
3. [EAT] 揚げまんじゅうを食べる(名物ベース・店指定なし)
4. [FACE] 五重塔をバックに最高の笑顔(Face Tracking)
5. [POSE] 雷門の前で万歳する(Body Tracking)

入力「江ノ島・半日・アクティブ」→
1. [GO] 江島神社の奥津宮まで登り切る(±50m=難しめ)
2. [DO] 海をバックに波と一緒に撮る
3. [EAT] しらす丼を食べる
4. [POSE] 展望灯台の前で灯台と同じポーズ(Body Tracking)
5. [QUIZ] 「奥津宮の鳥居の色は?」(GPS + 文字列一致)

## 7. ミッション UI 方針(setlog 風)

vlog アプリ setlog の UI をリファレンスにする(ユーザー決定):

| setlog の要素 | 本アプリでの対応 |
|---------------|------------------|
| 毎時 2 秒動画の撮影ログ | ミッション達成写真がログになる(判定の副産物がそのままコンテンツ) |
| 丸角タイルのログ一覧 | ミッションカード一覧。達成すると写真タイルに変わる |
| 分割画面で参加者を同時表示 | 対戦相手の達成状況をリアルタイム並列表示 |
| 招待コードで同じログに参加 | **対戦マッチング**: 同じコードで同じプラン(JSON)に参加 |
| 1 日の終わりに自動 vlog 化 | 旅行終了時に写真×心拍の時系列リザルトを自動生成 |

- 招待コード方式は「対戦相手とのスコア突き合わせ」の解にもなる(同期は Firebase 等を想定、要検討)
